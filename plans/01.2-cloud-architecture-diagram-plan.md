## Context

Plan 01.1 delivered System Context, High Level Solution and Logical Architecture views. Re-checking
against the MSAG guideline deck (`requirements/MSAG-Diagram-Preparation-Guidelines-v1.1.pdf`) surfaced
one still-missing category — slide 6b, "System Model — Technical aspect" (deployment/network/data-
transmission) — leading to a first draft of a Cloud/Deployment page. That draft was reviewed and three
pieces of feedback came back, which this revision incorporates:

1. **Route 53 must be shown** as the network entry point (DNS resolution before WAF/CloudFront/ALB) —
   the first draft omitted it because it isn't named in the SAD's prose, but an internet-facing
   deployment needs a resolvable entry point, so it belongs on the diagram (and is now added to the
   SAD too, §4 Layer 2).
2. **CI/CD deserves its own page**, not just a notes-panel mention — depicting the actual pipeline
   stages. The user chose **AWS CodePipeline + CodeBuild + CodeDeploy + ECR** (already named in
   passing in SAD §4 Layer 6/§8) over a self-hosted Jenkins alternative, specifically for cost: no
   idle build server to run or patch, pay-per-build-minute, a small flat per-pipeline fee — and it
   avoids introducing a second CI/CD tool alongside what AWS already provides managed equivalents for.
3. **Real AWS Architecture Icons, proper bounded-context containers, and zero overlapping lines.**
   The first draft used the same plain colour-block convention as pages 1-4. For infrastructure-
   specific pages depicting actual AWS deployment, real icons and AWS's own VPC/AZ/Subnet/Security-
   Group container conventions read as a genuine AWS architecture diagram rather than a generic box
   diagram — this is scoped to the two new pages only; pages 1-4 keep their existing, already-reviewed
   plain style untouched.

`target=`.

**Net-new convention, scoped ONLY to pages 5 and 6:** real AWS Architecture Icons and AWS group
containers replace the plain colour-block convention pages 1-4 use. This is a deliberate, scoped
departure — not a retroactive change to the rest of the file.

**Resource icon template** (every AWS component on pages 5-6):
```
shape=mxgraph.aws4.resourceIcon;resIcon=mxgraph.aws4.{name};fillColor={category-color};strokeColor=#ffffff;verticalLabelPosition=bottom;verticalAlign=top;align=center;fontSize=11;html=1;
```

scale proportionally if different**) with the caption BELOW the icon, not text inside a filled
rectangle — a real layout change from the plain-box convention. One icon represents one logical
service/instance; where a stage needs several replicas of the same service, one icon carries a caption
naming the count/scope (e.g. one Fargate icon captioned "auto-scaling 2–100 tasks") rather than
drawing many icons.

```

```
Confirmed: AWS Cloud = `group_aws_cloud_alt` (`#232F3E`); Region = `group_region` (`#00A4A6`); VPC =
`group_vpc2` (`#8C4FFF`); Availability Zone = `group_availability_zone` (`#232F3E`). **Not confirmed by
name** (used with an explicit flag): Public Subnet (expected `group_public_subnet`, green `#248814` per
AWS's own convention), Private Subnet (expected `group_private_subnet`, blue `#147EBA`), Security Group
(expected `group_security_group`, red `#DD344C`) — **verify these three exact `grIcon` strings against
the installed shape library's shape picker before finalizing**; if a name doesn't resolve, fall back to
`shape=mxgraph.aws4.group` with no `grIcon` (a plain dashed rectangle, still a valid group shape) rather
than guessing further.

**Anti-overlap principle** (addresses "lines should not overlap"): `jumpStyle=arc;jumpSize=8` already
handles incidental **perpendicular** crossings — MSAG guidance is "minimum arrows," not "zero
crossings," and an arc-jump where one line hops over another at a right angle is a standard, legible
technique already used on this file's existing pages. What this plan explicitly eliminates instead is
(a) two edges tracing a **coincident parallel path** (the original draft's flaw — 6+ edges sharing one
routing corridor) and (b) ambiguous shared exit/entry points at a busy node. Fix: every edge leaving or
entering a shared node gets an explicit, distinct `exitX/exitY`/`entryX/entryY` fraction, and every
group of edges that must travel the same general direction (e.g. NAT Gateway → six external providers)
gets staggered, parallel-but-offset corridors (distinct x or y offsets, never the same line).

**Tag-letter scheme** — page 5 reuses **G / V / N / D / E** (no collision with pages 1-3's A-E/A-F/M-X);
page 6 introduces **P / Q / R** (pipeline/deploy, security/config, observability — no collision with
any existing scheme).

### Notes panel (`ci-notes`, x=40 y=1310 w=1760 h=200)

1. Reading order: Source (P1) → CodePipeline (P2) orchestrates three sequential stages via a shared S3
   artifact bucket (P3) — Stage 1 Build (P4→P5), Stage 2 Infrastructure (P6, Terraform, manual approval
   gate), Stage 3 Deploy (P7, blue/green).
2. **Cost framing.** CodePipeline charges a small flat fee per active pipeline with no idle-time
   charge; CodeBuild bills only actual build-minutes — no idle build server to provision, patch or
   scale. Materially cheaper than a self-managed Jenkins controller running around the clock, and
   avoids a second CI/CD tool alongside AWS's own managed equivalents.
3. **Blue/Green mechanism.** Blue = current/live (P10), Green = new candidate (P11); CodeDeploy (P7)
   shifts ALB weighted-target-group traffic (P8) — the mechanism behind SAD §7's "blue-green
   deployment for zero-downtime releases."
4. **Rollback.** A CloudWatch (R1) alarm on ECS/ALB health during the traffic shift triggers automated
   traffic-back-to-Blue and Green deregistration — ties to §7's Resilience/Reliability row.
5. CodeBuild appears twice (P4, P6) — two distinct projects (app build/test, Terraform plan/apply), one
   managed service; mirrors the Cloud/Deployment page's own SNS/SES dual-appearance note.
6. CloudWatch (R1) and Secrets Manager/KMS/IAM (Q1-Q3) also appear on the Cloud/Deployment page
   (N7-N10) — same services, two different lifecycle moments (steady-state runtime there, deployment-
   time here), not a duplicate.
7. This page is a companion to the Cloud/Deployment page — it does not redraw the VPC/AZ/subnet
   topology. The ECS Service/task-set icons here stand in for the same Multi-AZ Fargate runtime (V3
   there); the ALB (P8) is the same Multi-AZ ALB (V1 there), not a second load balancer.
8. Q3 (IAM) is shown with no drawn edge, consistent with the Cloud/Deployment page's N9 — its role
   relationship applies uniformly to every pipeline stage.
9. Source Repository (P1) is rendered in the same to-be-confirmed/assumption style as the Policy
   Administration System (E3) on pages 1 and 5 — no source-control platform is named anywhere in the
   case study or SAD.

```markdown
### Deployment Topology

The diagram's fifth page, **Cloud / Deployment Architecture** (`eclaims-cloud`), translates the six
```
