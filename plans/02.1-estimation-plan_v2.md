## How the template works (established by inspection)

Six fixed sections **A–F** on the `Estimation` sheet. Column `A` carries structural markers (`S1` section, `T1` task, `A` activity, `T3`/`S3` terminators).

**Only these columns are inputs** on an activity row:

| Col | Meaning | Col | Meaning |
|---|---|---|---|
| `N` | Activity name | `Q` | # (count) |
| `O` | RFP mapping | `R` | x N (multiplier) |
| `P` | Unit name | `U`/`V`/`W` | Complexity split H/M/L — **must sum to 1 or 0** |
| `G` | Optional (Yes/-) | `X` | PDs per 1 Medium unit |
| `H` | Buffer (-/Low/Med/High → +10/15/20%) | `Z` | manual +/- |
| `I` | Extras (-/Unit Testing +25%/Unknowns +10%) | `K`/`AB` | Notes / assumptions |
| `J` | Exclude (Yes → effort 0, no error) | | |

Everything else is computed:

```
Y  = CEILING( ( Q<=1 ? X : ( sum(U:W)=0 ? Q*X
                           : ((Q*U)*(X*1.5) + (Q*V)*X + (Q*W)*(X*0.75)) * (R=0?1:R) ) ) + Z , 0.25)
AA = Y * (1 + extras%)
S  = CEILING( AA*(1+buffer%) * (1 + salesScale) , 0.25)      # salesScale = 0 when S5="No Change"
T  (task total)    = SUMIFS(child S, exclude J="Yes")
S  (section total) = CEILING(SUMIF(child T), 1)
```

Note the two short-circuits: when `Q<=1` the result is just `X+Z` (complexity and `R` are ignored), and when `U:W` are all zero, `R` is ignored too.

### Two hard constraints

1. **Row structure is frozen.** sheet2 carries 2,138 `conditionalFormatting` blocks, 133 merges, 565 outlined rows, 9 hyperlinks and 463 shared formulas — all with absolute refs. Inserting or deleting rows by XML surgery would corrupt it. Not needed: there are **240 activity rows across 54 tasks**, far more than we need. Unused rows get `J="Yes"` (Exclude), which zeroes effort without tripping the `AD` error check.
2. **Never write to `M`, `S`, `Y`, `AA`, `AD`, `L`, `T`.** These are the shared-formula columns (13 masters each). Overwriting a shared-formula master breaks every dependent cell. Verified: all 16 input columns hold literals, except 18 deliberate driver cells listed below.

## Implementation — preservation contract first

**Base file:** byte-copy `Mohan_eClaims_Estimates-v2.xlsm` → `docs/estimation/Utsav_eClaims_Estimates.xlsm`, then edit in place.

### The contract

Of the workbook's **78 zip parts, exactly three may differ in content** — `xl/worksheets/sheet2.xml` (Estimation), `xl/worksheets/sheet3.xml` (Schedule), and `xl/workbook.xml` (one attribute). **The other 75 parts must be byte-identical**, verified by SHA-256: `vbaProject.bin`, `styles.xml`, `sharedStrings.xml`, `theme1.xml`, all 20 images, all 3 drawings, `vmlDrawing1.vml`, 6 `ctrlProps`, 4 `tables`, 5 `printerSettings`, 4 `customXml` items, chart parts, and every `_rels`.

**The part list itself does not change** — same names, same count, same order. Earlier I planned to delete `calcChain.xml`; that is unnecessary and now ruled out. The edit never adds or removes a single formula, so the existing calc chain stays valid. Keeping it means the archive's shape is untouched.

**Do not use openpyxl.** It rewrites styles and is unreliable with a 490 KB macro workbook carrying charts, VML and 2,138 CF rules. Stdlib `zipfile` + targeted string surgery only.

**Do not round-trip sheet2 through ElementTree.** It would rewrite the `xmlns:mc` / `xmlns:x14ac` / `xmlns:xr` prefixes and `mc:Ignorable`, and re-serialize self-closing tags — a diff of thousands of lines in which a real error is invisible. Parse read-only for analysis; write via targeted replacement of individual `<c>` elements.

### Never touch

| | |
|---|---|
| **Rows 649–657** | Hidden VBA row-clone masters (`TEMPLATE_SECTION`). These are the prototypes the "add row / add task / add section" macros copy. Corrupting them breaks the template's macros with no visible symptom until someone clicks a button. |
| **`<sheetProtection>`** | SHA-512 hash + salt + `spinCount`. Verbatim. |
| **Column `A`** | Structural markers `W0/W1/S1/S2/T1/T2/A/T3/S3/M` that the VBA reads to find sections. |
| **Cols `B` `C` `F` `L` `M` `S` `T` `Y` `AA` `AD`** | Formula/marker columns, incl. all 463 shared-formula masters. |
| **Row elements** | Every `<row>` attribute preserved verbatim: `r`, `spans`, `s`, `customFormat`, `ht`, `customHeight`, `hidden`, `outlineLevel`, `x14ac:dyDescent`. Row count stays **596**, ids **1–659**. |
| **Sheet-level blocks** | `sheetPr/outlinePr`, `dimension`, `sheetViews` (incl. frozen pane), `sheetFormatPr`, `cols`, `mergeCells`, `dataValidations`, `conditionalFormatting`, `hyperlinks`, `pageSetup`, `drawing`, `legacyDrawing`, `extLst`. |
| **Defined names** | All 90 in `workbook.xml`, untouched. |

### Steps

0. Write this plan to `plans/02.1-estimation-workbook-plan.md` before starting the build.
1. Read every part into memory preserving name order; SHA-256 each one up front for the later diff.
2. Edit sheet2 by locating `<row r="N"[^>]*>.*?</row>` and, inside that slice only, replacing the single `<c r="REF"…>…</c>`. **Carry the existing `s=` style attribute across unchanged** on every cell written.
   - numeric → `<c r="Q23" s="…"><v>48</v></c>`
   - text → `<c r="N23" s="…" t="inlineStr"><is><t xml:space="preserve">…</t></is></c>`
     Inline strings avoid editing `sharedStrings.xml` at all. Escape `&`, `<`, `>`.
   - Guard: assert the target cell is not in the never-touch column set and its row is in 12–442 (or the explicit summary/RFP allowlist) **before** writing. A typo'd ref must fail loudly, not land on a formula.
3. Two cells do not currently exist and must be **inserted** rather than replaced: `Q402`, `Q403`. Excel requires cells in ascending column order within a row — insert before `R402`/`R403`, not appended. These are the only two additions; total cell count goes 16,410 → 16,412 and nothing else may change.
4. Reimplement the `Y → AA → S → T → section` chain in Python; iterate the `Q`/`R`/`X`/`U`/`V`/`W` inputs offline until every section total hits its target, then write the results into the cached `<v>` of the formula cells so the numbers read correctly even without a recalc.
5. Add `fullCalcOnLoad="1"` to the existing `<calcPr calcId="191029"/>` in `xl/workbook.xml` — attribute added, nothing else in that part changes — so Excel authoritatively recomputes on open.
6. Rewrite the zip with the original part order, `ZIP_DEFLATED`, `.xlsm` extension and macro-enabled content type.

Build the file to the scratchpad first, run the full verification there, and only copy into `docs/estimation/` once it passes. The build script is a throwaway and is not committed.

## Amendments made during the build

A few things surfaced only once the actual file was parsed cell-by-cell; recorded here rather than silently reconciled, since the numbers above were the plan and these are what actually shipped.

- **Section C's 33-task table summed to 550, not 520.** Re-adding the plan's own PD column gives 550. Since the six section totals (70/75/**520**/105/120/70 = 960) are internally consistent and 960 is the anchor carried from plan 02, the per-task table was trimmed by 30 PD across twelve of the larger tasks (Microservice base framework 18→16, CI/CD 16→14, Auth/RBAC 20→18, Claims Service 30→28, Incident Mgmt 24→22, Notification 18→16, Payment 20→18, Document 20→18, UI architecture 14→12, Shared UI framework 18→16, Customer Portal 34→30, Internal Portal 32→28) rather than changing the section target. The built workbook carries the corrected (520-summing) numbers.
- **`Q402`/`Q403` already existed** in the source file as empty self-closed cells (`<c r="Q402" s="134"/>`), not absent — so the fix is a plain cell edit, not an insertion. Cell count stayed at **16,410** throughout, not 16,412.
- **Column semantics differ by row type**, which the "How the template works" section above doesn't distinguish: `M` is a shared-formula auto-numbering column on activity (`A`-marker) rows, but a *literal, editable* task-name column on `T1`-marker rows — that's where the Section C task renames actually land. `T` is a formula (task-total) column only at `T1` rows; on activity rows it's simply unused. Actual complexity split lives in `U`/`V`/`W` as documented; a first pass misread it as `T`/`V`/`W` before checking the raw cell XML directly.
- **Moving the `Total_Screens` driver off `R402`/`R403` changes what those cells *are* — a formula becomes a literal, and a previously-empty cell gains a formula. `calcChain.xml` lists cell-level formula membership, so it goes stale the moment a formula cell's identity changes, even though the total formula *count* in the workbook is unchanged.** This tripped Excel's repair path silently under COM automation (`Workbooks.Open` throws `COMException: Unable to get the Open property of the Workbooks class` with no further detail — worth knowing if this happens again). Fix: `calcChain.xml`'s `r="R402"`/`r="R403"` entries are rewritten to `r="Q402"`/`r="Q403"`, keeping their existing `i=`/`l=`/`s=` attributes. So the preserved-parts contract is actually **`sheet2.xml` + `workbook.xml` + `calcChain.xml`** (not the two originally planned) — all three are still pure surgical edits, no shape change.
- **Buffer/extras were uniformly `-` (none) on every activity row in the source file**, rows 9–442, so `H`/`I` never needed touching — the `Z` (manual +/-) column was the only tuning knob actually used, and only on the 15 rows whose `Q` is formula-driven (`Total_FRs`/`Total_Use_Cases`/`Total_Test_Cases`/`Total_Screens`); everywhere else the built-in `Q≤1` short-circuit made the activity's `X` cell equal to its target PD directly.
- **The `Schedule` sheet (sheet3.xml) was left byte-identical**, not edited. Its phase-bars are style-only cells across an irregular, non-uniform column span per phase (no value, no formula — just fill styling), so lengthening a bar means inserting new cells rather than editing existing ones; given the risk/reward for a secondary Gantt view, this was descoped. It still renders (Gate 5), just shows the original file's bar lengths.
- **The FBS chart-data table (`M452:P492`) was updated** to the new Section C task/module names and PD/cost, even though it's a hardcoded snapshot the original macro populates (not a live formula) — confirmed stale even in `Mohan_eClaims_Estimates-v2.xlsm` itself (task 1 shows 13 PD there against the sheet's own 5). Module groupings (row spans) were kept identical to the source; only names and numbers changed, one module renamed ("Core Domain & Workflow Foundation") since its member tasks changed conceptually.
