## Document 1 — Workflow orchestration engine

**File:** `docs/dar/Utsav_eClaims_DAR.docx` · **Recommendation:** AWS Step Functions

SAD §8 states the conclusion: *Workflow — AWS Step Functions — managed state machine with a
built-in audit trail and no infrastructure to run*.

**Why the workflow engine.** It is the component with the greatest architectural leverage: it owns
the governed claim lifecycle, it is the source of the audit trail on which non-repudiation depends,
and it is the component whose later replacement would cost the most.

The Workflow Engine and Step Functions are already present in the SAD prose (§4 Layer 3, §4 Layer 2
VPC endpoints, §8 technology table) and in diagram pages 3, 4, 5 and 7 — so no diagram edits are
required.

### Candidates

Four options are scored. The fourth is included deliberately: it is the honest baseline, it is what
the POC already implements, and any engine has to justify its cost against it.

| Option | Category | Delivery model |
|---|---|---|
| AWS Step Functions | Managed state-machine service | AWS-managed, serverless |
| Camunda (Platform 8) | BPMN process orchestration platform | Self-hosted or vendor SaaS |
| Temporal | Code-first durable execution platform | Temporal Cloud or self-hosted |
| In-Service State Machine | Application-owned state machine | Runs inside the existing services |

The in-service baseline is real code, not a hypothetical: the role-gated state machine lives in the
`TRANSITIONS` map at [claims_service.py:15-22](../src/backend/claims-service/services/claims_service.py#L15-L22),
enforced by `validate_transition()` at
[claims_service.py:25](../src/backend/claims-service/services/claims_service.py#L25).

Considered and not carried forward, recorded in §3: Apache Airflow (data-pipeline orchestrator, not
a human-paced business process engine), AWS SWF (maintenance mode), Netflix Conductor and Flowable
(no capability the four above do not already represent).

### §4.4 Pricing — basis stated explicitly

Basis: 200M customers × ~6% annual auto-claim frequency ⇒ **~1M claims/month**; ~25 state
transitions per claim including choice states and retries ⇒ ~25M transitions/month.

| Option | Indicative monthly | Basis |
|---|---|---|
| Step Functions (Standard) | ~$625 | 25M transitions × $0.025/1,000; first 4,000/mo free; no charge for idle wait |
| Camunda 8 self-hosted | ~$685 infra + licence + ~0.5–1 FTE | 3× m6i.large Zeebe ≈ $210, RDS Multi-AZ ≈ $255, OpenSearch exporter ≈ $200, ALB ≈ $20 |
| Temporal Cloud | ~$1,000+ | ~40M actions/mo at ~$25/M plus retained-state storage |
| In-service state machine | $0 incremental | Runs in existing ECS Fargate tasks; cost shifts to engineering |

All figures are labelled **indicative public list prices as at the document date, not quotations**.


### §5 Recommendation

**AWS Step Functions (Standard Workflows)**, with the claim lifecycle as a state machine and human
steps as `waitForTaskToken` callbacks driven by the Internal and Partner Portals.

The recommendation carries its weaknesses on the record (no task inbox, ASL less expressive than
Python, one-year execution limit, no on-premise option) and carries an explicit fallback: **if
regulation or organisational policy mandates on-premise deployment, Camunda Platform 8 is the
alternative** — which is also how the dual cloud/on-premise NFR is satisfied. The fallback is
affordable only because business logic stays in the FastAPI domain services and out of the workflow
definitions.

### §6 Assumptions

AWS commitment (SAD §9 assumption 1) with Terraform keeping on-premise open; business logic stays
out of workflow definitions (this is what keeps the engine swappable, and is the R1 mitigation);
claim duration well inside the Standard 1-year limit; human tasks are portal-driven task-token
callbacks, not a Step Functions task inbox; **Phase 1 POC continues to run the in-service state
machine** (per SAD §8's closing note) — this DAR recommends for the target production architecture;
the stated volume basis; event emission to EventBridge is unaffected by the engine choice; pricing
is indicative; no existing Camunda or Temporal capability is assumed.

### §7 Risks

R1 AWS platform lock-in · R2 no native human-task UI · R3 cost growth at high transition volume
(Express Workflows for high-frequency sub-flows) · R4 late on-premise mandate (Camunda fallback) ·
R5 team familiarity with ASL · R6 one-year execution limit · R7 service quota and throttling.

**The honesty note in §8.2.** The original scored 7 attributes; this one scores 10. §8.2 reconciles
them line by line rather than leaving a reader to diff the tables:

- **4 new** — performance under load, OpenAPI generation, request validation, ecosystem maturity
- **1 dropped** — architecture type (describes the options, ranks nothing; kept descriptively in §4.3)
- **1 renamed and narrowed** — flexibility → microservices fit
- **pricing scored in neither** — all three are free of licence cost, so it cannot discriminate

The two decisive additions are OpenAPI generation and request validation, both weight 4, both
favouring FastAPI. §8.2 says plainly why: the original was built for a consumer retail website that
rendered its own pages and had no published interface contract, where neither mattered much;
eClaims serves three portals plus partner integration, where both are stated requirements. It
records that **excluding both still leaves FastAPI ahead (4.72 vs 4.28)** — they widen the margin
rather than create the outcome. It flags that the Deployment row is a correction of *fact*, not of
judgement. And it points out that the fourth new attribute, **ecosystem maturity, counts against
FastAPI** (4 vs 5 for both rivals) — included deliberately, since an added attribute set that
favoured the preferred option uniformly would be evidence of a matrix built backwards. FastAPI also
**loses** outright on extensibility, and merely **ties** on microservices fit, deployment, scaling
and complexity — four of ten attributes carrying 16 of the 40 weight. The matrix is not rigged.

§5 flips to FastAPI and carries its weaknesses on the record (blocking-call fragility, shallower
ecosystem, pre-1.0 versioning, no ORM/admin), states Flask as the closest alternative and *why the

### The on-prem NFR has a real soft spot — surfaced, not papered over

The SAD claims on-prem capability in three places — §7 NFR row ("Terraform IaC for both
on-premise and AWS"), §8 ("Multi-target (cloud and on-premise)") and Layer 6 ("enabling **both

## Build approach

`python-docx` is not installed and is not needed — Python 3.12 stdlib (`zipfile`, `xml.etree`) only.
The same builder produces all three documents; it is scratchpad tooling, not a repo deliverable.

1. Prose for each document is held in its own scratchpad content module (`content_backend.py`,
   `content_compute.py`) as a small document DSL, so wording is reviewable before it is sealed into
   OOXML and every §4 total is *computed from the score table* rather than typed as text.
2. A shared builder (`darlib.py`, driven by `gen.py`) reads `docs/dar/DAR Template.docx` and writes
   each target `.docx`, copying all 26 parts byte-for-byte except `word/document.xml` and
   `docProps/core.xml`. Table column widths are apportioned from relative weights to a fixed
   9026 dxa total, and each table is followed by an empty paragraph so Word does not merge adjacent
   tables.
3. `word/document.xml` preserves **verbatim** the `<w:document>` root and its namespaces, the
   cover-page content controls, the revision-history table, the TOC content control, and the
   trailing `<w:sectPr>`. Only the cached cover text and the first revision row are patched, and
   the TOC field is marked `w:dirty="true"` so Word repaginates on open. Body content is emitted
   between the TOC and the `sectPr` via `h()` / `p()` / `bullet()` / `table()` / `recommend()`
   helpers that use only the template's own style IDs.
4. **Headings emit a `pStyle` only.** `Heading1`–`Heading3` already carry `numId 37` in
   `styles.xml`, so adding `numPr` to a heading paragraph would double-number it.
5. `docProps/core.xml` is updated for `dc:title`, `dc:subject`, `dc:creator`, `cp:lastModifiedBy`
   and the `dcterms` timestamps. `docProps/app.xml` is left alone — its `Company` is already
   "Nagarro Software Pvt. Ltd.", which is what the cover's Company control binds to.

**Main risk:** hand-built OOXML that Word repairs or rejects.
**Mitigations:** minimum element set (`p`/`r`/`t`/`tbl`/`tr`/`tc` plus
`pPr`/`rPr`/`tblPr`/`trPr`/`tcPr`); `ElementTree.fromstring` on both rewritten parts *before*
packing; then a round-trip extraction of the finished file through `scratchpad/docx2txt.py`. The
prologue patch set is asserted rather than assumed — each of the three cover replacements must
match exactly once, and the revision row must expose exactly four empty cells, or the build fails.
